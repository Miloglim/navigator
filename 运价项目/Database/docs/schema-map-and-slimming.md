## 1. 先讲清关系：识别名 → 规范名 → 港群 → 业务值

```
        一个港口实体在库里的样子（ports 一行）
   ┌────────────────────────────────────────────────────────┐
   │ name(规范名/主键) = "Tianjin New Port"                  │
   │ name_cn "天津新港" · name_en(=name 1179/1190) · city    │
   │ locode_ref "CNTXG" · aliases "天津,新港,XINGANG,…"      │◀── 识别名（别名）
   └────────────────────────────────────────────────────────┘
                     │  启动时全部喂进 build_index
                     ▼
     port_idx: fold(每个识别名) → 规范名        ← 折叠 = 去音标/大小写/`.``,`-()`，无相似度
     name_idx: fold(规范名) → 规范名            ← 精确兜底
     规则：一个 fold 键指向 ≥2 个规范名 ⇒ 整条丢弃（宁可不归，不能归错）
                     │
   写入路径（三条入口同源）：
     群里/人工写的任意写法 ──fold──▶ 命中 ─▶ 业务表只存【规范名】
                                   未命中 ─▶ check_status=failed，进待审交人工
                     │
   港群（port_groups）：另一个"可以被当值使用的名字"
     name="MEX" label="墨西哥/Mexico" members="Manzanillo,Lázaro Cárdenas" kind=pod
     · 存值时：命中港群 ⇒ 业务表 pod 存【群名 MEX 一条】，不拆成员
     · 查询时：双向展开 ⇒ 筛成员港带出群价，筛群名带出成员价，非成员不串
     · 优先级：group_for() 先于 lookup_port() ⇒ 群名与港名同命名空间，不得撞名
   航线（routes）：region 只是分组元数据，不是识别名，不参与匹配（2026-09-11 修过这个 bug）
```

一句话记法：**业务表里永远只有规范名；识别名是入口，港群是"一个代表一片"的入口；两者都靠同一张 `Master` 索引折叠，折叠有歧义就一律不猜。**

## 2. 字段清单：谁写、谁读、是溯源还是结构

业务表 29/30 列，按性质分四组（`KEY_EXCLUDE` 已把后两组排除出内容指纹，是对的）：

| 组 | 列 | 性质 | 备注 |
|---|---|---|---|
| **核心值** | `pol` `pod` `carrier` `route` `container_type` `freight_usd`/`price_usd` `box_qty` `space_type` `vessel_voyage` `transit_days` `free_days` `dead_freight` | 结构化，参与指纹与身份键 | 全部归一到主数据 |
| **时间三件套** | `valid_from` `valid_to`（解析后 ISO）· `etd`（开船日 ISO）· `message_time`（群消息时间，排序用） | 结构 | `status`/过期由这几列**现算** |
| **溯源原文** | `validity_raw`（原文"9.13"/"ETD 9.16"）· `cutoff_raw`（截关原文）· `box_desc`（箱型箱量原文）· `message_text`（逐字原文，判重参与方） | 只读给人看，永不参与计算 | ⚠️ `validity_raw` 与 `etd` 不是重复：448 行两者都有、**值相同 0 次**，因为一个是原样抄、一个是解析结果 |
| **系统列** | `content_key`(指纹 UNIQUE) `mid`(消息ID) `supersedes`(留痕指回旧行) `status` `overridden_time` `synced_at` `origin` `ai_flag` `image_url` `image_file` | 机器写 | 其中 `image_url`/`image_file` **是同义双列**（见 3.B） |

## 3. 冗余清单（实测）与处置

### A. 可以现在删（业务表 0 行，删列=改 DDL，无数据迁移）

| 目标 | 实测证据 | 处置 |
|---|---|---|
| `ports.name_en` | 与 `name` 同值 **1179/1190** | 把不同那 11 行的值并进 `aliases`，删列（`build_index` 键源同步去掉） |
| `image_url`（两表都有） | 与 `image_file` 同义；中文键还分 `运价图片`/`舱位图`/`图片名` 三个；前端 **0 引用**，只有 `images_for` 三处兼容读 | 收敛成**一个**图片引用列 `image_file` + **一个**中文键 `图片名`；`images_for` 的英文键兼容留着即可 |
| `chat_groups.region` / `owner` | 填充 **0/11**；`owner` 前端有 4 处表单引用 | 删列 + 删前端那两个输入位（或改成真在用，见 D） |
| `city_pinyin` | 填充 40/1190，且 2026-09-12 已退出匹配键源 | 删列（拼音进 `aliases`，与其余别名同一真源） |
| `routes.note` | 0/25 | 保留（表间一致性成本为零），不再单独提 |

### B. 不是删列，是**停止双写**（收益最大的一处）

`aliases` 把别的列的值又抄了一遍：含规范名 **1178** 行、含 LOCODE **1170** 行、含 `name_cn` **372** 行。
而 `locode_ref` 这一列**根本不参与匹配**（不在键源里），能靠 `MXZLO` 命中全靠别名里那份手抄件。

后果：改 `locode_ref` 不改别名 → 命中失效，且没有任何地方会报错。

建议：把 `locode_ref` 加进 `build_index` 键源，然后**一次性清掉别名里的 LOCODE 抄件与规范名/name_cn 抄件**（约 1500 条），此后规则变成——
> **每类识别名只有一个家：规范名在 `name`，中文名在 `name_cn`，码在 `locode_ref`，其余俗称/缩写/错写才进 `aliases`。**

### C. 派生而非存储（"能算出来就别存"）

| 列 | 现状 | 建议 |
|---|---|---|
| `route` 航线 | 92% 有值，但它是 `pod` 的函数（`ID key changes.md` 已写明"航线由目的港派生，不进身份键"） | 保留为**缓存列**，但由闸门按 `pod` 自动派生并**覆盖人工填写**；派生不出来才留空。这样"航线填错"这一类脏值直接消失 |
| `pending_records.resolved` | 与 `payload` 内容重叠的归一缓存 | 保留（卡片显示"归一 X/Y/Z"要它），但注明是缓存、放行时必重算，不作为真值 |
| `status` | 已部分派生（当前/过期由看板 fold 现算），但 `已被覆盖` 是存的 | 维持现状即可，别再加派生层 |

### D. 整块没启用的结构负债：`operators` + 分区可见性

`operators` **0 行**，但代码里 `viewer`/`scope` 过滤贯穿四处查询入口、前端有身份切换 UI、`match_mode` 有引用。
两条路选一：**配人启用**（销售只看自己航线/群，这是当初的设计目的），或者**整块摘掉**（删表 + 删 scope 参数 + 删前端身份下拉）。
现在这种"结构在、数据空、逻辑跑着"的状态最费人：每次改查询都要考虑四处 scope 是否漏带。

### E. 主数据的 `source` 是复合串

330 行写成 `nominated:地中海:海港名精确`——把"来源类型 + 区域 + 采用方法"塞进一格，只能 `LIKE`，没法按区域查。
要么拆成 `source` + `adopted_by` 两列，要么承认它是审计文本、区域交给 `routes.region`。**别让它承担查询职责**（现在也没承担）。

## 5. 落地顺序与风险

1. **第 1 步（零风险）**：B 类——`locode_ref` 进键源 + 清别名抄件。纯主数据整理，不改表结构，改完 `manual_check` 里 `MXZLO→Manzanillo` 那条用例正好守住它。

3. **第 3 步（要口径）**：C 类 `route` 由 `pod` 派生覆盖——需要"目的港→航线"映射表（现在靠 `ports.aliases` 里混着的区域词，正是 338 条死别名的来源；清掉之后必须有显式映射，否则派生不出来）。这一步得先定：**要不要建 `port→route` 显式映射**（约 1190 行，可由 `source` 里的区域串一次性生成、人工复核）。
4. **第 4 步（要决策）**：D 类 `operators` 启用还是摘掉。

## 6. 航线两级结构（2026-09-12 按群聊语料定稿）

**航线是什么**：业务坐标，不是识别名。它承担五件事——分区授权（`operators.routes`）、看板分组与筛选、记录的归类标签、群画像的产出声明（`chat_sources.profile.routes`）、族级统计。**它不承担**"港口属于哪个区域"——那是 `port→route` 映射的活，过去寄存在 `routes.aliases` 的国家名和 `ports.aliases` 的区域词里，制造了 338 条死别名，已清理。

**两级**：族（6 个「××线」）只做分组/授权/统计，**不写进业务表**；子线才是 `route` 列的值。落地**复用 `routes.region` 存族名，零 DDL 变更**。

```
美加线  美东 · 美西 · 美湾 · 加拿大
欧地线  欧基港 · 北欧 · 波罗的海 · 地中海 · 地东 · 黑海 · 亚得里亚海 · 北非
拉美线  南美东 · 南美西 · 中美洲 · 加勒比 · 墨西哥 · 内陆河运
澳新线  澳新
亚洲线  红海 · 东南亚 · 中东 · 印巴 · 日韩 · 港澳台 · 远东 · 中亚
非洲线  东非 · 南非 · 西非        （原 非洲东岸/南岸/西岸 改名，旧名进别名）
```

**四条争议用语料定的**（语料 = 群原始消息 + 识图缓存 + LLM 判定 + 待审，共 2850 条）：

| 争议 | 命中 | 结论 |
|---|---|---|
| 「欧洲」是否合并 北欧/欧基港/波罗的海 | 欧基港 807/49 源，群里写 `POD欧基:Hamburg/Rotterdam/…`；识图 route 字段是 `地东/黑海/欧基港` **并列** | **不合并**；"欧洲"降级为 `欧基港` 的别名 |
| 地东 是否并入地中海 | 地东 435/58 源（"宁波 地东现仓"、"上海-地东 ETD9/18"），地中海 398/105 | **独立子线保留** |
| 巴拿马 是否独立子线 | 巴拿马 231 次，上下文全是 `巴拿马科隆`（目的港）与 `不经巴拿马`（运河路径），报价挂在加勒比线下 | **不建子线**；"巴拿马/科隆/colon"改挂 `加勒比` 别名，并从 `中美洲` 别名里撤出 |
| 澳新 是否拆三条 | **0 命中** | **不拆**，等真出现报价 |

**两条纪律**：

- **0 命中的子线只建名、不配 `port→route` 映射**（加拿大/印巴/中亚/远东/港澳台 部分），按"识别入库过程中逐渐完善"的路子走，不预先造映射表。
- **国家名与港名不做航线别名**：`巴西/阿根廷/智利/秘鲁/hamburg/rotterdam/ca` 这类一律从 `routes.aliases` 撤出——它们要么与别的航线撞（`ca` 同时是加拿大和中美洲，实测就撞了），要么把国家当航线。国家归属走 `ports.country`。

**一处后果要你知道**：`SAWC`（南美西的服务码）原先挂在 `南美西` 别名里，那 28 条待审是**靠它才通过校验**的；本次按"服务码不是航线"撤掉后，这 28 条转为 `航线「SAWC」不在主数据里` 交人工。要恢复自动归一，把 `SAWC` 加回 `南美西` 别名即可（一行）。
