# Agent 数据传入契约（freight_manual.db）

> 面向：识别群聊运价/舱位信息后、要把结果写进本台账的 agent。
> 本文只规定**数据以什么形式传入**（需求 7-2）。怎么从群聊里识别、清洗、判重，agent 侧自理，不在本文范围。
> 目标：核心字段 100% 标准化——**只能落在主数据预设值上**，杜绝脏值污染库（需求 7-1）。

配套实现见 `docs/standardization-review-spec.md`（校验规则、待审核流程）。

---

## 1. 传入方式（唯一入口）

agent **不直接写业务表**，一律 POST 到待审核暂存口，经机械校验 + 人工放行后才落库：

```
POST /api/pending
Header: x-push-token: <写入令牌>
Body:
{
  "kind": "rates",              // "rates"=运价库 | "space"=舱位库（服务端 kind / table 两个键名都收）
  "origin": "agent",            // 固定 agent，用于和人工录入区分
  "records": [ {中文字段记录}, {中文字段记录}, ... ]   // 一次最多 1000 条
}
```

- 每条 record 是一个**中文字段名 → 值**的对象（键名见下表，必须用中文键，和人工录入完全一致）。
- 服务端对每条跑机械校验：核心字段解析不到主数据 / 必填为空 / 价格非整数 → 该条 `check_status=failed`，进待审核页由人工处理，**不会污染业务表**。
- 校验通过（passed）的条目也要**人工点"放行"**才入库；放行时服务端自动判"新增 or 更新"（起运港+目的港+船司+原文全同＝更新，走留痕）。

> **运价/舱位共用一套字段并集**：顶层 `kind`（rates/space）只是一个提示，人工在待审核卡片上可一键互切重判。
> agent 不必纠结"这条到底算运价还是舱位"——把识别到的字段照上面两张表的**并集**填全即可，缺谁补谁，分类交给人复核。
>
> **第三类 `kind = "group_suggestion"`（港群候选）**：字段 `港群 / 标签 / 类型(pol|pod) / 成员(逗号分隔，必须是 ports 规范名) / 来源群 / 消息ID / 消息原文`。
> 它**不落业务表**，放行时写入的是主数据 `port_groups`（只补缺成员、不覆盖人工维护的标签与特例港）；成员里有虚构港名会整条 failed。
> 用途：agent 发现某群反复用某缩写代表一片港时提候选，由人工在「港群建议」页签定夺——港群是放大器，不让机器直接改。
>
> **合并港口非法**：一个字段里塞多个港（如 `Santos/曼萨尼约`、`ORF、PEL`）不合规。**一条记录只能有一个港**，
> 多港就拆成多条分别传；只有确实是维护过的**港群**时，才用群名（如 `NEB`）存一条。服务端暂存时也会按 `PORT_SEP` 兜底拆分，但 agent 侧应自己拆好。
>
> **中文/别名/拼音服务端归一**：`起运港` 传 `青岛`、`天津` 也会被 `lookup_port` 归成规范英文名（`Qingdao` / `Tianjin New Port`），
> 传中文不影响标准化；但直接传规范英文名最稳。

主数据（港口/船司/航线/港群的合法值）从这个只读口取，agent 归一时以它为准：

```
GET /api/master?full=1     // 港口(含别名/中英/拼音/LOCODE/国家)、船司、航线、港群、发送人
```

## 2. 运价库记录（kind = "rates"）

字段名＝数据库中文列名。**规范值**列说明该字段必须长成什么样。

| 中文字段键 | 库列 | 必填 | 类型/规范值 | 标准化要求 |
|---|---|---|---|---|
| `起运港` | pol | ✅ | 主数据港口规范名（英文官方名，跨国重名带国家后缀如 `Manzanillo(MX)`）**或**港群名 | 必须命中 `ports` 或 `port_groups`；可填别名/中文/拼音/LOCODE，但**建议 agent 直接给规范名** |
| `目的港` | pod | ✅ | 同上 | 同上 |
| `船司` | carrier | ✅ | `carriers.code`（如 `MAERSK`/`CMA`/`MSC`） | 必须命中 `carriers`；给 code 最稳，给中文名/别名也可（服务端归一） |
| `航线` | route | 空可，填了必须命中 | `routes.name`（如 `南美东`） | 命中 `routes`，否则报错 |
| `柜型` | container_type | ✅ | 枚举：`20GP` / `40HQ/HC` / `40NOR` | 只能这三档，其它值拒收 |
| `海运费USD` | freight_usd | ✅ | **非负整数**（不带货币符/千分位/小数） | `2850` ✅；`2850.5`/`$2,850` ❌ |
| `有效期起` | valid_from | ✅(与止至少一端) | ISO 日期 `YYYY-MM-DD` | 严格 ISO |
| `有效期止` | valid_to | ✅(与起至少一端) | ISO 日期 `YYYY-MM-DD` | 严格 ISO；不得早于起 |
| `船期ETD` | etd | ✕ | `YYYY-MM-DD`（建议 ISO） | — |
| `AI判断` | ai_flag | ✕ | `是` 或留空 | agent 侧有效期兜底标记：报价无有效期也无开船时间时，skill 用「消息日→消息日+2天」兜底并置此值；看板据此显示"AI判断"标签提示人工核对。不参与内容指纹（改标签不产生新行）。 |
| `T/T航程` | transit_days | ✕ | 非负整数（天） | — |
| `目免` | free_days | ✕ | 非负整数（Freetime 天） | — |
| `亏舱费` | dead_freight | ✕ | 非负整数（USD） | — |
| `消息原文` | message_text | ✅ | 群聊原报价文本 | **参与新增/更新判定**，务必原样带上，别改写 |
| `来源群` | source_group | ✕ | 群名（建议在 `chat_groups` 里） | — |
| `发送人` | sender | ✕ | 人名 | — |
| `备注` | remark | ✕ | 自由文本 | — |
| `消息ID` | mid | ✕ | 群消息唯一 ID | 有就带，利于溯源/去重 |
| `运价图片` / `图片名` | image_url / image_file | ✕ | 图片引用（文件名） | 库只存引用名；看板从 `Database/images/<文件名>` 取真实文件显示，缺文件渲染"图片未同步"。agent 把下载到的原图存进该目录、`图片名` 填该文件名即可 |

> 不需要传：`记录状态`、`被覆盖消息时间`、`序号`、`更新目标`。
> `消息时间`：**agent 一定要传真实群消息时间**——服务端只在 `origin=manual`（人工录入）时才盖当前时间，`origin=agent` 时保留你传的值；折叠视图/历史轨迹都按 `消息时间` 排序，不传或传错会让当前价判定错乱。

**运价 record 示例**：

```json
{
  "起运港": "Nansha",
  "目的港": "Santos",
  "船司": "MAERSK",
  "航线": "南美东",
  "柜型": "40HQ/HC",
  "海运费USD": 2850,
  "有效期起": "2026-09-10",
  "有效期止": "2026-09-16",
  "船期ETD": "2026-09-18",
  "T/T航程": 35,
  "目免": 7,
  "消息原文": "MAERSK 南沙-Santos 40HQ 2850 9.10-9.16",
  "来源群": "南沙-南美东运价群",
  "发送人": "张三"
}
```

## 4. 标准化红线（agent 必须遵守，否则条目被打回）

1. **核心字段只能取主数据预设值**：起运港/目的港 ∈ `ports.name` 或 `port_groups.name`；船司 ∈ `carriers.code`；航线 ∈ `routes.name`（或空）。**不得出现预设以外的自造值**——拿不准就先查 `GET /api/master`，或宁可留空让人工补，也别编。
2. **港群**：一条报价覆盖多个港时，用港群名（如 `NEB`）存**一条**，不要拆成成员港多条；库里存群名，查询端会自动双向展开。
3. **有效期**用 `有效期起`/`有效期止` 两个 ISO 日期，不要传 `9.10-9.16` 这类区间串（那是人工批量导入才解析的写法）。
4. **价格/天数一律非负整数**，不带单位、千分位、小数。
5. **柜型三档、舱位类型八档**，严格照枚举。
6. **消息原文原样带上**：它是新增/更新判定的键之一，改写会导致重复入库。
7. agent **只写 `/api/pending`**，不碰 `/api/push`、`/api/record/*`、`/api/master/*`（那些是人工口子）。放行动作永远由人做——agent 不得自行入库。

### 4.1 引用原文 → 单向判更新

某条消息若是**引用回复**旧报价，`record_builder.compose_text` 会把被引用的旧消息逐字附在本条原文后，用一条分隔行隔开（不是单独字段，全拼进 `消息原文` 这一个串）：

```
<本条逐字全文>

——引用 <被引用时间(截到分钟)> <被引用发送人> mID=<被引用消息 openMessageId>——
<被引用消息逐字全文>
```

台账的更新判定按**单向**处理这段引用：

- 本条原文带 `——引用…mID=X——` 时，先按 `mID`（旧行 `消息ID`）精确命中、再退回"被引用正文 == 旧行 `消息原文`"定位被引那条（**允许它是已被覆盖的老版本**）；随后顺 `supersedes` 链向后解析到该身份的**当前生效版**，把更新覆盖到当前版本 → 走留痕。即便有人越过最新版去引用两周前的老报价改价，也不会分叉出两个"当前生效"。
- **只允许"引用方 → 被引用方"这一个方向**：绝不因为"甲原文包含乙"就反推"乙更新甲"；也绝不把"被引用"当成当前行去覆盖新行；更不因"没有引用块"就断言一定全新（仍走 `起运港+目的港+船司+原文` 的精确判定）。
- 无引用的普通消息，`消息原文` 就是你本条逐字全文，行为不变。同一回复 + 同一引用重复投递得到同一串 → 同一指纹，不堆重复。

## 5. 回执与状态

`POST /api/pending` 返回 `{ok, staged, ids}`——只表示"已暂存待审"，**不代表已入库**。
人工在"待审核"页放行后，条目才进业务表；`check_status=failed` 的条目会带 `errors`（哪个字段、传了什么、为什么不合规），agent 侧可据此回捞重传。

查询侧（供 agent 读价，只读、免写令牌）：`GET /api/rates`、`/api/rates_grouped`、`/api/space`、`/api/space_grouped`，筛选参数 `pol/pod/carrier/route/ctype/group/status` 等，港群自动双向展开。
