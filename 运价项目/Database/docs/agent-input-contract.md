# Agent 数据传入契约（freight_manual.db）

> 面向：识别群聊运价/舱位信息后、要把结果写进本台账的 agent。
> 本文只规定**数据以什么形式传入**（需求 7-2）。怎么从群聊里识别、清洗、判重，agent 侧自理，不在本文范围。
> 目标：核心字段 100% 标准化——**只能落在主数据预设值上**，杜绝脏值污染库（需求 7-1）。

配套实现见 `docs/standardization-review-spec.md`（校验规则、待审核流程）。

---

## 1. 传入方式（唯一入口）

外部解析 Agent 统一调用 `POST /api/agent/intake/v1`，使用独立 `Authorization: Bearer <NAVIGATOR_AGENT_API_TOKEN>`。该入口校验版本化信封后复用同一个待审核实现；本机采集器继续调用 `POST /api/pending`。两者都只暂存待审核，经机械校验 + 人工放行后才落库。

外部入口的字段、示例和脚本见 `Skill/navigator-agent-intake/`。接口不接受直接发布、审核或主数据写入。

内部采集器契约：

尚未形成可核实结构化报价的消息不适用本入口：采集程序自动调用 `/api/review-issues` 保存原文、原图引用与阻塞原因，显示在航管“待审核 > 待核问题”区。它不是报价，不参与机械通过统计或一键放行；接口失败时保留采集水位并重试。

```
POST /api/pending
Header: x-push-token: <写入令牌>
Body:
{
  "kind": "rates",              // "rates"=运价库 | "space"=舱位库（服务端 kind / table 两个键名都收）
  "origin": "agent",            // 固定 agent，用于和人工录入区分
  "preserve_other_sources": true, // 完整来源的 Agent 默认开启：不撤换其他消息
  "preserve_existing_source_rows": true, // 仅补同一消息缺项时显式开启
  "records": [ {中文字段记录}, {中文字段记录}, ... ]   // 一次最多 1000 条
}
```

- 每条 record 是一个**中文字段名 → 值**的对象（键名见下表，必须用中文键，和人工录入完全一致）。
- 服务端对每条跑机械校验：核心字段解析不到主数据 / 必填为空 / 价格非整数 → 该条 `check_status=failed`，进待审核页由人工处理，**不会污染业务表**。
- 校验通过（passed）的条目也要**人工点"放行"**才入库；放行时服务端自动判"新增 or 更新"（起运港+目的港+船司+原文全同＝更新，走留痕）。
- **同一消息修复后补漏行**必须同时传 `preserve_other_sources: true` 与 `preserve_existing_source_rows: true`，并优先只传确认缺失的产品。服务端命中同源已有产品时保留原 `id / entry_id / edit_log / payload`，只插入缺项；默认采集提交仍按同源最新快照撤旧留新。回执用 `staged/ids` 表示本次新增，用 `preserved/preserved_ids` 表示原样保留，`covered_ids` 是本次覆盖核查的并集。
- **消息级条款字段会被补齐（只补空、不改值）**：`目免 / T/T航程 / 亏舱费` 这类整票只写一次的条款，若同一条 `消息ID` 拆出的多行里只有一行填了值，闸门把该值补进其余空行；组内出现两个不同值时**不动**（业务上免箱期确实可能按柜型分档）。响应里的 `inherited` 列出补了哪几处——采集端仍要逐档带全，别依赖兜底。
- **同一条消息的子条目整组归属（判定不变）**：同源视图按归一化消息ID派生归属，筛选后展示完整消息组；组内有未过时，已通过条目仍显示真实的"通过"结论。普通条目视图保持逐条筛选。不能为了整组展示或放行条件把已通过条目改成未过。
  所以 agent **必须把同一条来源消息拆出的所有记录填同一个 `消息ID`**——不填就各自成组、拿不到整组归属，审核员会在"已通过"里只看到一半柜型。
  「一键放行整组已通过」按同一来源消息的全部待审运价/舱位共同检查：只有**整组都通过且在当前操作范围内**才放行。组内有未过时整组暂缓，放行时重新校验失败也整组回滚；不影响单条人工放行。

> **运价/舱位共用一套字段并集**：顶层 `kind`（rates/space）只是一个提示，人工在待审核卡片上可一键互切重判。
> agent 不必纠结"这条到底算运价还是舱位"——把识别到的字段照上面两张表的**并集**填全即可，缺谁补谁，分类交给人复核。
>
> **第三类 `kind = "group_suggestion"`（港群候选）**：字段 `港群 / 标签 / 类型(pol|pod) / 成员(逗号分隔，必须是 ports 规范名) / 来源群 / 消息ID / 消息原文`。
> 它**不落业务表**，放行时写入的是主数据 `port_groups`（只补缺成员、不覆盖人工维护的标签与特例港）；成员里有虚构港名会整条 failed。
> 用途：agent 发现某群反复用某缩写代表一片港时提候选，由人工在「港群建议」页签定夺——港群是放大器，不让机器直接改。
>
> **合并港口非法**：一个字段里塞多个港（如 `Santos/曼萨尼约`、`ORF、PEL`）不合规。**一条记录只能有一个港**，
> 多港就拆成多条分别传；只有确实是维护过的**港群**时，才用规范群名（如 `Brazil North Ports`）存一条。已登记别名 `NEB`、`NE ports`、`北巴` 可传入，由程序归一到该规范群名。服务端暂存时也会按 `PORT_SEP` 兜底拆分，但 agent 侧应自己拆好。
>
> **中文/别名/拼音服务端归一**：`起运港` 传 `青岛`、`天津` 也会被 `lookup_port` 归成规范英文名（`Qingdao` / `Tianjin New Port`），
> 传中文不影响标准化；但直接传规范英文名最稳。

主数据（港口/船司/航线/港群的合法值）从这个只读口取，agent 归一时以它为准：

```
GET /api/master?full=1     // 港口(含别名/中英/拼音/LOCODE/国家)、船司、航线、港群、发送人
```

港群的`n/name`是规范名，`a/aliases`是识别别名，`l/label`是中文标签，`m/members`只含港口规范名。可用只读`POST /api/master/resolve`传`source_group`及`items:[{type:"pod",value:"NEB"}]`查询；只有status=resolved才可采用canonical。unknown/ambiguous/invalid_target不得猜规范名，不自动新增港口或港群。港群识别已切换，其他名称仍作shadow对照，以现有预检结果和差异处理阶段为准。

## 2. 运价库记录（kind = "rates"）

可选独立产品字段：`航线服务` → `service_name`（如 Ipanema/Carioca/Santana），`目的码头` → `destination_terminal`（如 TERPORT VILLETA）。原文明示时必须逐项提取；同港不同服务/码头分别提交，不得把多套价格压到备注。两项参与待审去重、放行覆盖、销售折叠和查询，空值不推断。

字段名＝数据库中文列名。**规范值**列说明该字段必须长成什么样。

| 中文字段键 | 库列 | 必填 | 类型/规范值 | 标准化要求 |
|---|---|---|---|---|
| `起运港` | pol | ✅ | 主数据港口规范名（英文官方名，跨国重名带国家后缀如 `Manzanillo(MX)`）**或**港群名 | 必须命中 `ports` 或 `port_groups`；可填别名/中文/拼音/LOCODE，但**建议 agent 直接给规范名** |
| `目的港` | pod | ✅ | 同上 | 同上 |
| `船司` | carrier | ✅ | `carriers.code`（如 `MAERSK`/`CMA`/`MSC`） | 必须命中 `carriers`；给 code 最稳，给中文名/别名也可（服务端归一） |
| `航线` | route | 空可，填了必须命中 | `routes.name`（如 `南美东`） | 命中 `routes`，否则报错 |
| `柜型` | container_type | ✅ | 枚举：`20GP` / `40HQ/HC` / `40NOR` / `45HQ/HC` | 按当前业务口径，入口值 `40GP` / `40DC` / `40DV` 归入 `40HQ/HC` 价格档；45HQ/45HC 仍独立存储 |

| `有效期起` | valid_from | ✅(与止至少一端) | ISO 日期 `YYYY-MM-DD` | 严格 ISO |

| `船期ETD` | etd | ✕ | `YYYY-MM-DD`（建议 ISO） | — |
| `AI判断` | ai_flag | ✕ | `是` 或留空 | agent 侧有效期兜底标记：报价无有效期也无开船时间时，skill 用「消息日→消息日+2天」兜底并置此值；看板据此显示"AI判断"标签提示人工核对。不参与内容指纹（改标签不产生新行）。 |
| `T/T航程` | transit_days | ✕ | 非负整数（天） | — |
| `目免` | free_days | ✕ | 非负整数（Freetime 天） | — |
| `亏舱费` | dead_freight | ✕ | 非负整数（USD） | — |
| `消息原文` | message_text | ✅ | 群聊原报价文本 | **参与新增/更新判定**，务必原样带上，别改写 |
| `来源群` | source_group | ✕ | 群名（建议在 `chat_groups` 里） | — |
| `发送人` | sender | ✕ | 人名 | — |
| `备注` | remark | ✕ | 自由文本 | — |
| `消息ID` | mid | ✕ | 群消息唯一 ID | 有就带，利于溯源/去重 |
| `运价图片` / `图片名` | image_url / image_file | ✕ | 图片引用（文件名） | 库只存引用名；看板从 `Database/images/<文件名>` 取真实文件显示，缺文件渲染"图片未同步"。agent 把下载到的原图存进该目录、`图片名` 填该文件名即可 |

## 4. 标准化红线（agent 必须遵守，否则条目被打回）

1. **核心字段只能取主数据预设值**：起运港/目的港 ∈ `ports.name` 或 `port_groups.name`；船司 ∈ `carriers.code`；航线 ∈ `routes.name`（或空）。**不得出现预设以外的自造值**——拿不准就先查 `GET /api/master`，或宁可留空让人工补，也别编。
2. **港群**：一条报价覆盖维护过的港群时，用规范港群名（如 `Brazil North Ports`）存**一条**；已登记别名由程序归一。不要拆成成员港多条，查询端会自动双向展开。
3. **有效期**用 `有效期起`/`有效期止` 两个 ISO 日期，不要传 `9.10-9.16` 这类区间串（那是人工批量导入才解析的写法）。
4. **价格/天数一律非负整数**，不带单位、千分位、小数。
5. **柜型最终仍为四档、舱位类型十一档**；入口值 `40GP` / `40DC` / `40DV` 按业务口径归入 `40HQ/HC`，45HQ/45HC 归一为独立的 `45HQ/HC`。
6. **消息原文原样带上**：它是新增/更新判定的键之一，改写会导致重复入库。
7. agent **只写 `/api/pending`**，不碰 `/api/push`、`/api/record/*`、`/api/master/*`（那些是人工口子）。放行动作永远由人做——agent 不得自行入库。

### 4.1 引用原文 → 单向判更新

某条消息若是**引用回复**旧报价，`record_builder.compose_text` 会把被引用的旧消息逐字附在本条原文后，用一条分隔行隔开（不是单独字段，全拼进 `消息原文` 这一个串）：

```
<本条逐字全文>

——引用 <被引用时间(截到分钟)> <被引用发送人> mID=<被引用消息 openMessageId>——
<被引用消息逐字全文>
```

台账的更新判定按**单向**处理这段引用：

- 本条原文带 `——引用…mID=X——` 时，先按 `mID`（旧行 `消息ID`）精确命中、再退回"被引用正文 == 旧行 `消息原文`"定位被引那条（**允许它是已被覆盖的老版本**）；随后顺 `supersedes` 链向后解析到该身份的**当前生效版**，把更新覆盖到当前版本 → 走留痕。即便有人越过最新版去引用两周前的老报价改价，也不会分叉出两个"当前生效"。
- **只允许"引用方 → 被引用方"这一个方向**：绝不因为"甲原文包含乙"就反推"乙更新甲"；也绝不把"被引用"当成当前行去覆盖新行；更不因"没有引用块"就断言一定全新（仍走 `起运港+目的港+船司+原文` 的精确判定）。
- 无引用的普通消息，`消息原文` 就是你本条逐字全文，行为不变。同一回复 + 同一引用重复投递得到同一串 → 同一指纹，不堆重复。

## 5. 回执与状态

`POST /api/pending` 返回 `{ok, staged, ids}`——只表示"已暂存待审"，**不代表已入库**。
人工在"待审核"页放行后，条目才进业务表；`check_status=failed` 的条目会带 `errors`（哪个字段、传了什么、为什么不合规），最终未过留在待审核交人工；常规采集Agent不据此循环修复或重传。

查询侧（供 agent 读价，只读、免写令牌）：`GET /api/rates`、`/api/rates_grouped`、`/api/space`、`/api/space_grouped`，筛选参数 `pol/pod/carrier/route/ctype/group/status` 等，港群自动双向展开。 `ctype` 支持逗号分隔四档多选，`route/group` 为精确匹配；`valid_since=YYYY-MM-DD` 取当日及之后仍有有效时间的记录，旧 `valid` 仍查询覆盖单日。

## Agent修复维护补充（2026-09-28）

用户已授权有依据地补齐缺港/群内别名，不等于开放通用管理员接口。使用`/api/agent/master/ensure`提交具体来源消息、群及官方/群知识证据，只新增不覆盖。对已有未审核Agent记录使用`/api/agent/pending/repair`，提交原payload签名防并发覆盖；原始来源与人工审核决定不可修改。详细字段见IPC契约。

常规JSON首次预检失败由Agent修正一轮源数据，重建后直接pending，不再复检。pending内部最终校验未过保留failed/awaiting及errors交人工，不回到Agent修复、不重复提交。取消例行用户确认。只推进已成功送审的来源水位，DONE不表示全部校验通过。


## 航次矩阵修复与身份保护（4.2.0）

舱位产品身份包含柜型、船名航次和ETD。两端都明确且不同的ETD不得按有效期重叠归并；只在一端未报ETD时保留原兼容归并。运价明示船名航次也结构化保存。`POST /api/agent/pending/repair`在已有证据、签名和未审核Agent限制下允许修复船名航次、舱位类型、AI判断，并可选传`kind=rates|space`纠正分类；记录kind修改审计，保持entry_id、orig_payload、来源与awaiting。审核和正式表权限不变。

## 钉钉来源身份（6.12.0）

自动采集报价透传可选 `来源群ID`（配置 cid）、`发送人ID`（原消息 senderId）、`发送人OpenID`（原消息 senderOpenDingTalkId）。模板和 LLM 后处理均从原消息取值；模型输出不能覆盖。继续全自动 `/api/validate` → `/api/pending`，不得手工导入。未知身份自动建立未绑定来源并接收入待审，管理员首次绑定账号后后续自动归属。不要把登录账号、昵称或 publisher_name 当稳定来源编号，不提交猜测的 publisher_id。

## 跨群自动归属（6.14.0）

同一原始人员ID在所有采集群复用同一publisher_id；来源群不限制账号归属。发送人ID与OpenID继续只取原始消息，不由模型、登录名或昵称生成。采集、校验、待审提交仍全自动；不需要逐群管理员绑定。没有人员ID的输入不能凭同名归属现有账号；同条消息的两个ID指向不同身份时拒绝静默合并。
