# ID key changes · 身份键变更记录

> **这是什么**：台账判断"两条记录是不是同一条报价/舱位(即该走更新留痕,还是各自独立并存)"用的**身份键**,是全系统最容易踩坑、也最需要留痕的地方。
> **规矩**:凡是改动"新增/更新判定"用到的字段(代码里 `manualdb.py` 的 `IDENTITY_COLS`、`_find_current_by_identity`、`classify_new_or_update`),**必须在本文件追加一条**,用人话写清:改前怎么判、为什么改、改后怎么判、影响面。别只改代码不留痕。

判更新的入口有两处口径,都写在 `manualdb.py`:
- `_find_current_by_identity`:在**业务表**里按身份找"当前生效"的那条(命中=判更新/留痕)。
- `classify_new_or_update`:给**待审核**卡片显示"新增/更新"徽标 + 暂存 target_key。
- 另有一条**单向引用链**(原文带 `——引用…mID=…——` 指向被引那条)也算更新,独立于身份键。

## 2026-09-11 · 身份键去掉「消息原文」,改用产品字段(柜型/ETD/船名)

- **改前怎么判**:同一条 = `起运港 + 目的港 + 船司 + 消息原文` 完全相同 → 判更新(留痕);否则新增。
- **为什么改**:一条群聊报价原文(尤其转发的多港/多柜型/多船次大表)被 heartbeat/expand 拆成多条记录后,**这些不同的报价共用同一条"消息原文"**。用"原文"当身份,会把**同一目的港的 20GP 与 40HQ、甚至不同船次/ETD** 误认成"同一条改了价",于是彼此标 `已被覆盖` → 出现假"无有效价"(实例:ZGWL·地东 40HQ 被同原文的 20GP 顶掉)。
- **改后怎么判**:身份=**产品维度**,不含原文——
  - 运价 rates:`承运人 + 起运港 + 目的港 + 柜型 + ETD`
  - 舱位 space:`承运人 + 起运港 + 目的港 + 船名航次 + 舱位类型 + ETD`
  - 完全逐字段重复(含原文)由 `content_key` 指纹天然幂等,不堆重复;真正"同一条产品改价/改有效期"才命中身份 → 走留痕更新。
  - 这跟 heartbeat 的口径一致:同一港口**不同船期/ETD 是两个航次、各自当前生效,不互相覆盖**。
- **影响面**:
  - `push`、`/api/pending` 暂存、`approve` 放行留痕,判"新增/更新"全部走新身份键。
  - 引用链(单向)判更新逻辑不变,叠加在身份键之上。
  - 历史误覆盖数据:本次不管(台账即将清空重建)。
- **未含的字段（有意）**:`航线` 不进身份(由目的港派生,避免空航线/派生差把同一条拆两半);`价格/有效期/Freetime/来源群/发送人` 都不进身份(它们是"这条报价的属性/改动内容",不是"哪条报价")。若将来要按"来源群"隔离(跨群各存一份),再在此追加。


### 配套：待审核入队「同产品身份·撤旧留新」（2026-09-11）
`stage_pending` 入待审时，用同一套产品身份（rates：船司+起运+目的+柜型+ETD；space 再+船名航次+舱位类型）比对已有**未处理(待审)**条目；命中就先删旧条、只留最新一条。解决"连拉最近几天同一报价的多次更新"在待审刷屏，以及"先放新价、再放旧价把旧价顶回当前生效"的顺序坑。业务表层的更新留痕逻辑不变。
