# 微调规则（用户口径，必须遵守）

### 0. 引用图片边界（2026-10-23）

引用消息里的图片只用于可展示副本和 SHA-256 哈希校验，不是本条报价的解析证据。只有当前消息自己的图片可以进入 vision、extract 和独立盘点；引用正文可帮助判断补充、修订或追问关系，但不能因为引用图片里有价格表就重新生成产品。展示图下载成功就写入 `图片名`；展示图失败只记录原因，不阻塞本条自己的文字或图片解析。

> 从 SKILL.md 移出的完整细则。判定入库前按需查阅，不必全文进上下文。
> record_builder.py 已内置其中可编码的规则（柜型四档、附加费进备注、有效期解析、无金额港点跳过）；
> 本文件用于 LLM 复核 med/high 置信度记录和模板未命中消息时的口径依据。

> ⚠️ **2026-09-10 台账化改版**：入库对象是「运价台账」`POST /api/pending`。**字段中文名、枚举合法值、核心字段必须命中主数据、价格整数、有效期 ISO、消息时间必带**等口径以 `Database/docs/agent-input-contract.md` 为唯一权威；下文第 3 条已按台账改写。抽取与判定口径（柜型三档、有效期解析、引用回复、原文逐字、附加费进备注等）仍然适用。柜型/舱位类型枚举台账不兜底，`pipeline.py` 自守；主数据缺口（华南基本港等）见 `references/learnings.md` 待观察。

1. **起运港三级判定**：① 消息正文明示的港口优先（SHEKOU→蛇口、YANTIAN→盐田、XINGANG→天津新港、NINGBO→宁波、QINGDAO→青岛、NANSHA→南沙）；② 否则取群名中的地名；③ 群名无地名则统一填 `华南基本港`。COSCO 那种"全口岸"列表照原样写入，别压缩成单个港。**注意**：台账核心字段必须命中主数据，`华南基本港` 这类语义港群需已在台账 `port_groups` 登记，否则相关记录会以 `failed` 进待审核（见 `learnings.md` 待观察）。
2. **航线分类与舱位目的范围**：沿用工作台口径（欧基港/地东/地西/北非/黑海/亚德里海/希腊/中东/东南亚/美西/美东）+ 已扩展的 `加勒比`/`南美东`/`南美西`/`墨西哥`/`中美洲`。**台账里 `航线` 填了必须命中 `routes` 主数据**。舱位必须有可检索的目的范围：`目的港/港群`、`航线`、`航线服务`至少一项。`地中海`这类地理范围填`航线`；`WSA/WSA2/MD1/MD3`这类产品码填`航线服务`；都不得塞进`目的港`。原文无法确定三者中的任何一个时保持 failed，不能只凭船名或箱量发布。
3. **同航线同有效期只认最新一条，旧价不删除、不就地改写**，因此：
   - 按 `航线 + 有效期 + 船司` 分组，组内取 `createTime` 最大的那条作为**当前事实源**
   - **agent 只产新记录，不改旧行、不写任何状态回写字段**。改价/售罄一律由 LLM **产出新记录（insert）**；旧行不动，"当前价"由台账折叠视图 `fold` 现算（`/api/rates_grouped` 每组默认展示当前、其余进历史）
   - 台账对**同 `起运港+目的港+船司+原文`** 的提交会自动判"更新（留痕）"而非堆重复行——所以同一条报价重发不会产生脏数据，`消息原文` 逐字尤其重要
   - 若旧消息含新消息没有的港点（如补充航次），合并两者港点集合，但价格以最新为准
   - 判定"是否同一条"要同 `来源群`（跨群转发各存一份，互不覆盖）且有效期/船期口径一致；同一港口不同船期（9.5 船 vs 9.8 船）是两个航次，都算当前生效，不是覆盖
6. **柜型四档，与入库契约保持一致**：`20GP`、`40HQ/HC`、`40NOR`、`45HQ/HC`。
   - `45HQ` / `45HC` / `45尺高柜` → `45HQ/HC`，独立配价、独立入库，不映射为40HQ/HC。明确45尺报价时按原价提取；加价公式仅在基准报价、币种与适用范围均明确时计算并保留依据，否则保留原文待核。只有“可接45HQ”“不接45HQ”等说明而无报价依据时，仅保留条件备注，不生成45尺价格；不得因页面新增价格列而猜价。
   - **柜型未明示时必须参考相似航线或相近港口价格判断（2026-09-30 用户再次重申）**：不能仅因原文未写柜型就直接留空、丢弃或只写“待核对”。优先查同船司、同航线或相近港口、相近消息日期/有效期、可比起运范围及费用口径的已确认柜型报价；优先本群同发布人，其次本群其他已确认报价，再查可比群来源。有唯一稳定口径时必须填写柜型，`备注`记录参照消息、港口或价格形态并标 `AI判断=是`，不把判断伪装成原文明示。只有多个可比参照相互冲突、确实无法排除时才保留未知；不得改原价迁就判断，也不把单价一律设成高柜。一个字段不确定时，其余明确的港口、价格、船期和船名仍须完整提取。
   - `小` / `20'` / `20GP` / `20DC` → `20GP`
   - `高` / `40HQ` / `40HC` / `40'HC` → `40HQ/HC`。明确分列的 40GP 与 40HQ 仅在同价时合并；异价保留并交审核，不能无条件把 40GP 改成高柜（与下文规则21一致）。
   -  `NOR` / `40NOR` / `40'NOR` → `40NOR`
   - 三段报价串带 NOR 标记，如 `5600/5900/5200NOR` → 按 `20GP` / `40HQ/HC` / `40NOR` 各配一个价，不因第三档有后缀把整串判成未知。不凭空增添第四档 40GP。
   - 只有两段且上下文支持常规小柜/高柜顺序（如 `6600/6900`）→ `20GP` + `40HQ/HC`；明确表头优先，不能把三段串举成两段例子。
   - 只有三段且未注明柜型（如 `6600/6900/6700`）→ `20GP` + `40HQ/HC` + `40NOR`。**先检查已确认的群 + 发送人专属口径**：`qingdao_latam` 韩琦的 MSC 南美东价卡 `A/B/B` 只生成小柜和高柜；未独立标 NOR 就不补 NOR，详见本群 `规范.md#韩琦柜型识别口径`。不将这项例外推广到其他来源。
   - 若某张表 40GP 与 40HC **确实不同价**，不要擅自合并：保留两条并在备注标注"40GP/40HC 不同价，需人工确认柜型口径"
   - 运价规律，在任何常规情况下，同一条消息柜型运价永远都是20GP<40NOR<40HQ/HC
7. **停接/无报价港口不入库**：表中标 `/`、`N/A`、`SUSPEND`、`case by case`（即拿不到金额）的港口直接跳过，不产生空价格记录。但**标红写"停接"且仍有价格**的港口要入库，并在备注**开头**标注 `停接（暂停接载）；` 便于筛除。
8. **跨群重复不去重**：同一条报价被转发到多个群时，每个群各存一份，保留"哪个群发的"这个粒度。不要按内容指纹合并。
9. **只入运价，不入动态**：现舱/配额/箱子开舱/截数据通知/操作提醒/@人催单类消息一律不入运价表。但"指导卖价""成本价""合约价"这类带报价的即便挂在现舱消息里也要入。判定看**有没有金额**：`9.6 特价合约 CALLAO 多出一个NOR现舱，价格超低` 无价→不入；`msk线上现舱 QINGDAO-COBUN 5X40HQ 9.5，15 天ft，USD6887` 有价→入。
10. **有效期冲突**：以图片表头为准入库，并在备注里注明两说（如"表头有效期9.8-9.14，消息正文写9.7-9.14"）。
11. **有效期必须解析成日期列**：`有效期船期` 保留原文自由文本用于展示与溯源，同时必须解析出结构化列，否则做不了过期灰显和跨周涨价对比。统一调用 `scripts/validity_parser.py` 的 `parse(text, msg_date)`，禁止各处自己写正则，避免口径漂移。三类情况：
   - **周次型有效期**（适用于所有群，不限船司或航线）：`WK43`、`43周`、`第43周`、`Week 43` 以及带年份的 `2026年第43周` 都是有效期表达。统一按消息年份的 ISO 周历换算成周一至周日，例如 `2026年第43周` → `2026-10-19` 至 `2026-10-25`；保留原文到 `有效期船期`。周号不是 ETD、PCD、截关日，也不能按消息日+2天兜底。只有在上下文明确它是船名航次/服务编号的一部分时，才不当有效期解析。多图或多周号必须按各自图就近绑定，不能合并或让后一周覆盖前一周。
   - **区间型**（`9.1-9.7`、`9/1-9/7`、`9.1~9.7`、`9.1-14`、`2026/09/01~09/07`、`1 Sep - 7 Sep`）→ 填 `有效期起` + `有效期止`，`船期ETD` 留空
   - **单开船型**（`9/7开`、`9.12 ETD`、`ETD：9.8`、`8.31托9.8`、`9/6晚开9/9`、`ETD SHEKOU 6/SEP`）→ 只填 `船期ETD`（取实际开船日期），`有效期起/止` 留空。这类没有有效期，不要拿开船日硬凑成区间。
   - **晚开/延误船期（所有群通用）**：`A晚开到B`、`A晚开B`、`A晚开至B` 表示原计划 A 开，延误后改为 B 开，必须填 `船期ETD=B`，不能取 A。例：`10.22晚开到10.28` → `船期ETD=2026-10-28`。不能把 A-B 写成报价有效期，也不能因 A 早于消息日期而丢掉 B。
   - **不可解析**（`case by case`、`锁8月底运价+500`、空）→ 三列全留空，原文照抄进 `有效期船期`
   - **年份推断**：默认取消息所在年份；若解析出 `起月 > 止月` 说明跨年，`止` 年份 +1；若 `起` 月份比消息月份大超过 6 个月，视为上一年（跨年回卷）
   - **GRI 不是有效期**：`9.08 GRI 1,000/1,000/1,000` 是综合费率上调生效日，写进备注，不要解析成有效期
   - **展示文本与解析输入可以不同**：`有效期船期` 照抄群里怎么写的（`9.8-14`），但若这句解析不出来，用 `add(vparse=...)` 传图内表头原文（`Validity 8 SEP- 14 SEP 2026`）给解析器。只允许"补全"，不允许改数
   - **归一化例外**（record_builder.py norm_v 已内置）：`9/8--9/14` 双横线先归一为单横线；`9.6晚9.8` 补成 `9.6晚开9.8`；`8-Sep to 14-Sep` 补成 `8 Sep - 14 Sep 2026`
   - 配套视图：在表格里建视图对 `有效期止` 加条件格式（早于今天→灰底），并按 `起运港+目的港+柜型+船司` 分组、`有效期起` 排序，即可看同一条线的涨价 diff
11. **附加费归备注**：PCTS/PCS/EFS/FAF/碳排放/GFS/危险品PG分级/重量附加/内陆费 add on 等全部写进备注，**不要**加到海运费数字上，海运费永远保持原报价裸价。价格后缀 `+` 通常表示后面另带附加费缩写或附加费未展开（如 `5200+`、`4150/4550+ISPS/AMS`），不是不确定价格；抽取时 `海运费USD` 只取 `+` 前裸价，`+` 及其后的附加费缩写写进备注，不因此降置信度。
12. **只有加价公式、没有完整独立报价的港点**：如 `RIO GRANDE addon +USD250/500`、`PYASU add on +1000/1200/1200 on top of ECSA BP`。公式原样保留在对应报价备注，写明基础港群；**不生成柜型和海运费均为空的独立待审条目**。需要另列报价时须有完整柜型与价格依据，不把附加费金额直接当海运费裸价。2026-09-28用户纠正：此前“保留空报价交人工”造成凭空多出3条，废止该做法。
13. **FAK 绝对价优先保留**：图上明确列出 FAK 价格时，运价库必须录入图上 `海运费USD`；正文中的 BASKET/T0、折扣、成本调整、利润或附加费只写入 `备注`，不得因为这些说明清空图上 FAK 金额。只有纯公式且没有图上绝对价格时，才省略价格和柜型并进入人工核对。
13. **消息原文必须逐字全文（引用回复附带被引用原文）**：`消息原文` 字段直接取 `dws chat message list` 返回的 `content`，**原样照抄**——保留 `@所有人`、换行 `\n`、加粗星号、删除线 `~~…~~`、emoji、中英文标点、多余空格。严禁用 `|`、`…`、省略号压缩，严禁改写、润色、重排或只摘关键句。若这条是引用回复，`消息原文` 由 `record_builder.compose_text()` 装配为「本条全文 + 一行 `——引用 <时间> <发送人> mID=<被引用消息ID>——` + 被引用消息全文」，两段都保持逐字、不改写。同一条消息派生的所有记录，其 `消息原文` 必须完全一致（拼法确定，可作台账新增/更新判定与内容指纹的稳定键）。落地做法：一律从 `.work/msgs_*/<slug>.json` 的 `c`/`q` 反查，生成器里手打原文即视为违规。
14. **溯源完整性**：每条记录必须带 来源群+发送人+消息时间+消息原文（全文）+运价原图。纯文字报价无图时，附件字段留空即可。
15. **并列多港同价必须拆港**：一行覆盖多个并列目的港且共用同一套价格（如 `CAUCEDO/KINGSTON/CARTAGENA`、`BUENAVENTURA / CALLAO / VALPARAISO`、`CALDERA / ACAJUTLA / SAN LORENZO / CORINTO`）时，必须拆成多条记录，每条只填一个目的港，其他字段照抄。斜杠 `/`、顿号、中文/英文逗号只有在明显表示并列港时才拆；`GUANTA,VENEZUELA` 这类“港名,国家”不是并列港，不拆。同一基本港因**走不同航线/挂靠港**给出不同价时（MSC `via IPANAMA / via CARIOCA / via SANTANA`），把走法并进目的港字符串区分（`基本港 via CARIOCA`），不要合并成一条。
16. **引用回复（quotedMessage）必须解析**：`dws chat message list` 对引用回复会返回 `quotedMessage{content, createTime, openMessageId, sender}`，被引用的原消息全文（含图片 mediaId）一起带回来，**不需要回拉历史**。群里大量关键状态就藏在引用里：
    - 回复"无 / 售罄 / 没了 / 满了"引用某条现舱 → 把被引用那条对应的舱位记录标「已被覆盖」（能对上 openMessageId 就按它定位），引用本身不单独成行
    - 回复带调价（"还有200左右的空间""5个以上再减100""+500/CNTR"）引用旧报价 → 以被引用报价为基价生成新记录，备注写"基于 <原消息时间> <原发送人> 的报价，本轮另减/另加 X"；**没有绝对金额就海运费留空**，别自己算
    - 被引用消息常早于水位线（如 9/1 引用 8/25 的报价）→ 这是正常现象，按引用内容入库，不要因为原消息不在窗口内就丢弃
    - `消息原文` 由 `compose_text()` 自动附带被引用原文（本条全文 + `——引用 <时间> <发送人> mID=<被引用消息ID>——` + 被引用逐字全文），记录自带引用上下文；备注里**只补一句引用结论**（如"售罄""基于原报价另减X"+引用时间），不要把被引用全文再抄一遍进备注
    - 拉消息的 `--jq` 必须带上引用字段，否则等于丢信息：
      `--jq ".messages[] | {t:.createTime, s:.sender, id:.openMessageId, img:[.resourceRefs[]?|.resourceId], c:.content, q:{t:.quotedMessage.createTime, s:.quotedMessage.sender, id:.quotedMessage.openMessageId, c:.quotedMessage.content}}"`
      落盘 `msgs_*/<slug>.json` 时 `q` 一并存。
16.1. **Izmit / Izmir 独立港口消歧（2026-09-29）**：`Izmit`（伊兹密特）与 `Izmir`/`İzmir`（伊兹密尔）不是别名。原图英文、中文、LOCODE/主数据和所在行必须一致后才能归一；OCR 只给相似英文时不得猜测。`ALIAGA (IZMIR码头)`仍归 `Aliağa`，不归 `Izmit`；`GEBZE/IZMIT`中的 `IZMIT`也不能被改成 `Izmir`。历史错误别名 `Izmit→Ambarli`废止，Ambarli只按Istanbul语境处理。

17. **目的港/起运港写法（台账匹配实测口径，2026-09-10 校准）**：台账匹配是"折叠后精确命中"（`fold()` 只去音标/大小写/`.` `,` `'` `-` `()`，无相似度），**同名多国必须消歧**。按可靠性排序：
   - 一条记录只能有一个起运港和一个目的港。以 `/`、`、` 或 `,` 并列的港口必须逐港拆成独立记录；明确已登记的港群名可保留。`Hongkong` 统一写为主数据规范名 `Hong Kong`。
   - **首选 LOCODE / 中文名 / 常见英文名**：`MXZLO`、`COCTG`、`TRMER`、`USORF`、`曼萨尼约`、`Norfolk` 都能命中；`ORF/PEL/BAL`（美东三字码）、`ISTANBUL`（→Ambarli）、`ALIAGA`（→Aliağa）已在主数据登记为别名，发原样即可。
   - **带国家后缀的写法只有"已登记成规范名"的才命中，不是通用格式**：实测 `ports` 里带括号的只有 7 行（`Caldera(CL)`/`Caldera(CR)`、`Cartagena(CO)`/`Cartagena(ES)`、`Port Elizabeth(US)`/`(ZA)` 等真跨国同名港），这些走 name_idx 精确命中、可依赖（闸门用例已钉成回归项）。但 **`Manzanillo(MX)` 命中不了**——库里只有一个 `Manzanillo`（country=MX，别名含 `MXZLO`），巴拿马那个 Manzanillo 根本没登记（而 `CAR`/`MEX` 港群成员串里却写着 `Manzanillo(PA)`/`Manzanillo(MX)`，属主数据不一致，待补）。**所以别给任意港名硬加 `(XX)`；消歧一律首选 LOCODE（`MXZLO`/`COCTG`）或中文名。**
   - **裸同名港判歧义 failed**：`Cartagena`（CO/ES 同名）、`卡塔赫纳`（中文也同名）→ 必须带 LOCODE。COSCO 加勒比表里的 Manzanillo 是巴拿马（`Manzanillo, PA`），PIL/MSK 墨西哥线的是墨西哥（`MXZLO`），**按航线上下文选对那个**。
   - **`中谷` 能命中**（是 `ZGWL` 别名），别当缺失；`CLSAI`→`San Antonio` 是**正确命中**（CLSAI 是圣安东尼奥智利的 LOCODE），不是误伤。真正要小心的是别把报价里的纯数字/产品代号当港口发。
   - **真缺的港**（如 `Aliağa`、美东三字码）走人工维护补进 `ports` 主数据（`/api/master/save`），不是 agent 自动写；agent 仍"识别到什么发什么"，命中不了交台账判 failed。
17. **有效期兜底窗（2026-09-10 定稿：运价、舱位都必填）**：`VALIDITY_REQUIRED_KINDS={rates,space}`，两库都强制有效期非空。报价常只给船期不给区间，统一走 `validity_parser.derive(text, msg_date)` 三级补，返回 `(有效期起, 有效期止, 船期ETD, ai_default)`：
   - **有明确区间**（`9.15-9.21`）→ 直接用 `有效期起/止`，**不标 AI判断**。
   - **无区间但有开船时间 ETD**（`9/16`、`9.12 ETD`、裸日期 `2026-09-16`）→ `有效期起=消息日`、`有效期止=开船日`（即"当前时间→开船时间"，"当前时间"取**消息日期**保证可重放），**不标 AI判断**。
   - **既无区间又无 ETD**（`case by case`、空、纯产品代码）→ `有效期起=消息日`、`有效期止=消息日+2天`，并置 `AI判断=是`。
   - **联动看板**：`ai_default=True` 的记录，运价/舱位看板在"有效期"处渲染"AI判断"标签（`ai_flag` 列），提示有效期是 AI 兜的、需人工核对。落地：`record_builder.rate/space` 与 `pipeline.step_build` 合并 LLM 记录时都调 `vdates`（=norm_v+derive），据 `ai_default` 写 `AI判断` 字段。
18. **船名里的公司 ≠ 船司（共船 / 舱位互换 VSA 是常态）**：能识别到 `船名航次`（如 `MSC OSCAR / 2637W`、`COSCO SHIPPING ...`）就把整串**照抄进 `船名航次`**，但**绝不能**从船名里那个公司名（MSC/COSCO/…）反推、回填 `船司` 字段——很多船司**共船、互相租舱（VSA）**，船东 ≠ 出这票舱位/报价的承运。`船司` 只能取自**报价来源**：群画像 `profile.carriers`、正文明示的承运人、发送人语境；三者都没有就 `船司` **留空**交台账判 failed，**别拿船名硬凑**。审/改时也别把"船司 ≠ 船名里的公司"当错误去"纠正"成船东。
19. **合并船司必须原样传串，禁止"取第一家"**（2026-09-11 事故：宁波群 `EMC/COSCO`、`HPL/ZIM/MSK` 被写成 `EMC`、`HPL`，伴生船司静默丢失，而且**校验照样通过**）。台账闸门已会按 `/ 、 ,` 拆分并逐个归一到 `carriers` 主键：全命中 → 自动展开成 N 条（每司一条，共舱语义）；任一 token 未命中 → 整条打回。所以 skill 侧**只管照抄原串**，不要自己挑一家、也不要预先拆。未知但形态像船司缩写的 token（2-6 位大写字母）台账会自动补一条 `carriers` 主键并在 `note` 里留"auto：待人工复核＋来源群/发送人/消息ID/原文"，人工可否决——**skill 不写主数据**。
20. **表头没有目的港列时，分段标题就是目的港**（2026-09-11 事故：宁波群空班/加班船表按 `南美西墨西哥 / 加勒比 / 南美东` 分段，判定层当成"没有目的港"，于是把 ETD 格里的说明文字硬塞进 `目的港`）。正确做法：`加勒比`→`CAR`、`南美东`→`ECSA`、`墨西哥`→`MEX`、`南美西`→`WCSA`（**按港群名存一条，不拆成员**）；`南美西墨西哥`这种合并段 → 同一行**存 WCSA、MEX 两条**。ETD 文字里出现"墨西哥加班船"这类区域词同样回填 `目的港`。
21. **多档柜型必须逐档配价**：`柜型="20GP/40HQ/HC/40NOR"` 时 `海运费USD` 要给 `"100/200/300"` 三个价，台账按位配对展开；只给一个价会被逐条打回（**闸门绝不把一个价复制给三档**）。另外别把 `40GP`（普柜）写成 `40HQ/HC`（高柜）——台账已取消那条悄悄归一，`40GP/45GP` 一律按"柜型只三档"打回。
22. **服务码 / 航线缩写 / 占位说明不是港口**：`WSA/WSA2/MD1/MD3`这类明确服务码写`航线服务`；`地中海`这类已登记区域写`航线`。`ESE`、`BP`、`Base Port`、`Port group`、`NE Port`、`Argentina 1`、`(未注明，只去Manzanillo/Lazaro/ESE)` 等无法可靠确定含义的内容不得填进`目的港`，原文保留在备注并让条目保持 failed，不再允许以空目的范围放行。
23. **占位符不是值**：`船名航次`、`目的港`、`船司` 拿不到就**留空**，不要写 `(未注明船名)`、`未注明`、`待定`、`无`（此前有 22 条占位符船名"通过校验"，放行就会往台账写假船名）。台账对占位符一律按未填打回。注：`船名航次` 自 2026-09-18 起是**选填**——现舱消息常只报"某港还有几高柜"根本不给船名，留空不再被判缺必填，只有写了占位符才打回。
24. **一格多船期拆多条；被放弃的行不得静默丢**：`9.6和9.13 墨西哥加班船` → 两条记录，各自带 ETD。表里判断不入库的行（如整段"X号跳港NB"）必须在同批某条记录的 `备注` 里写明"本图另有 N 行跳港未拆"——2026-09-11 那张图 OCR 只留 14 行、实际 39 行，缺的 25 行**没有任何提示**，这属于丢数据。多维合并（船司×港口×柜型）展开超过 60 行时台账只落一条"超过上限"工单交人工，所以**能按原文配对就配对传，别指望闸门做笛卡尔积**。
25. **港群/航线归属的出口是"提候选"，不是自己改字典**：发现某群反复用一个缩写代表一片港（如 `NBE` 指巴西北部几港），**不要**直接往 `port_groups` 加成员——港群是放大器，一个成员加错会让整群价被错误展开。正确做法：`POST /api/pending` 带 `kind=group_suggestion`，字段 `港群 / 标签 / 类型(pol|pod) / 成员(逗号分隔，必须是 ports 规范名) / 来源群 / 消息ID / 消息原文`，人工在待审页「港群建议」签放行才真正写入；成员里有虚构港名会整条打回（报"成员港不在 ports 规范名里"）。同理，**航线是港口的子属性**（`ports.route`，台账已按港群成员种子化，航线空缺时按目的港派生）：采集侧发现某港航线缺失，也只提候选、不猜值。
26. **同一条消息拆出的记录必须带同一个 `消息ID`**：同源视图按消息归组展示全部柜型，条目视图和一键放行按每条自己的校验结果处理。组内有未过条目不改写已通过结论，也不阻止放行其他已通过条目；未过条目继续待审。`消息ID`从原始消息逐字带入，不按柜型另造ID。

27. **带价现舱双入：运价 + 舱位**（2026-10-22 用户口径）：任何带价格的条目都先产一条 `rate`；若是“带价现舱/SPOT/现舱表”，同时再产一条同源 `space`。金额只写运价的 `海运费USD`；运价只接收兼容字段（港、船司、柜型、海运费、ETD、船名航次、有效期、备注），`价格USD`、`舱位类型`、`箱量/箱型箱量`等字段只写舱位。两条记录保持同一 `消息ID`，完整原文只作共同溯源。无价格的现舱动态仍只产 `space`。判定特征包括 `10.6 上海-IST 3750 1高 A.P.MOLLER/638W` 和现舱表 `RATE + VOLUME`。

28. **舱价同源按行双入**（2026-10-22 用户口径）：消息可同时包含独立价格区和舱位动态区。纯价格行只入 `freight_rates`；无价舱位动态行只入 `space_records`；同时带价格和舱位事实的行按规则 27 双入，运价保留兼容字段，舱位保留箱量/舱位类型/截关等专属字段，金额只在运价。
29. **消息级条款字段必须逐档柜型带全**：`Freetime：10days 【HDL USD 25/柜】`、`T/T 35 days`、亏舱费这类**整票只写一次**的条款，拆成 20GP / 40HQ/HC / 40NOR 多行时**每一行都要照抄同一个值**——只挂在第一行会让看板 F/T 列一半空，审核员看着像「没识别出来」（2026-09-22 实例：同一条 MSC 欧洲报价，20GP 带了目免 10、40HQ/HC 空着）。闸门已加兜底：同 `消息ID` 内某条款字段只有唯一非空值时自动补进空行（响应 `inherited` 给明细）；但**这是兜底不是借口**——两档填了不同值时闸门不会动（业务上免箱期确实可能按柜型分档），别指望它替你判断。另：`HDL USD 25/柜` 是**超期堆存费**，不是免箱天数，留在 `备注`，绝不允许塞进 `目免`。

30. **Freetime/FT 必须独立成「目免」字段，不要只塞备注**（2026-09-22 edit_log 学习沉淀）：消息里出现 `Freetime：10days`、`14天FREE TIME`、`FT 4+12`、`14天FT` 这类写法时，**把天数提取到 `目免`（FT/free_days）字段**，值为数字天数（如 `10`、`14`）。禁止只把整句抄进 `备注` 而让 `目免` 留空——这是过去 4 次人工修改的共同原因。配套：`HDL USD 25/柜`、超期堆存费、demurrage 等仍留备注，不进 `目免`；`FT 4+12` 这种"免箱+超期"写法，`目免` 取前半段免箱天数（`4`），`+12` 写备注。

31. **目的港里混进的航线产品代码要剥出来写备注**（2026-09-22 edit_log 学习沉淀）：`欧洲基本港NAC`、`GdanskFAL1` 这类"港群名/港名+航线产品码"粘连写法，**目的港只留港群名/港名**（`欧洲基本港`、`Gdansk`），**产品代码（NAC/FAL1/FAL3 等）挪进备注**（如 `NAC 服务`、`FAL1 航线`）。判定：全大写 2-5 字母、紧跟在港名后面、不是港名本身——它是航线/服务代码不是地名，放进 `目的港` 会导致主数据匹配失败或把港群名变成脏值。欧洲价格群内 `GDK/FXT` 中，`GDK` 是 `Gdansk`（格但斯克）缩写，`FXT` 是 `Felixstowe`；不得把 GDK 当成 Gdynia，也不得把这类港口缩写留在未解析状态。


32. **全局航管识别与报价内容分开**（2026-09-28 用户口径）：本人发过 `@所有人` 是强业务依据；消息数量明显高于普通成员、按已结束工作日统计且长期稳定是联合依据。一群可有多人，不只挑最多的一位。引用中的群发不计给回复者；缺采集不能算零，新人未命中不能认定非航管。账号、采集覆盖证明、初始阈值和当前使用边界见 `publisher-identity-rules.md`；该规则不改历史审核/校验结论。

32. **价卡分类先读本图定义**（2026-09-29）：ECSA Base Port 1、Argentina 1、US2 Port group等分类若本图底部列出明确成员，按该图成员匹配；无定义才留未知交人工。不能无条件清空，也不能将本图分类并入不同成员的现有港群。via写已有航线服务字段，缺via仅称“原表未列经由”；完整保留页脚和费用适用范围。
### 模板结构指纹闸门（2026-09-30）
- 只有历史结构稳定的模板登记指纹；至少核对规范港口名称集合、港口数量、生成条目数量和产品身份是否重复。

## 2026-10-08 v3 新增规则（防错误报价入库优先）

### 33. 消息意图分类（防询价/操作通知被复制成报价）

**以当前消息的行为判断，不是以被引用消息判断**：

| 当前消息特征 | 判定 | 处理 |
|---|---|---|
| 有明确金额 + 价格表/报价格式 | 报价 | 正常入库 |
| 有金额但在问句里（"2800 能接吗"、"3100 还能做吗"） | 询价 | 不产新报价，标"询价" |
| 无金额 + 问价/能走吗/还有吗 | 询价 | 不产新报价，标"询价" |
| 开舱/截关/催单/放舱/@人 | 操作通知 | 不产报价 |
| 引用报价 + 本条是调价（"降 200"、"改 3100"） | 调价 | 标已覆盖，不产新行 |
| 引用报价 + 本条是问（"还有吗"、"能接吗"） | 询价 | 不产新报价 |

**关键修正**：
- ✅ 被引用是报价，本条是航管回复真实价格 → 正常入库（不是询价）
- ✅ "2800 能接吗" 有金额但仍是询价（问句格式）
- ❌ 不再"被引用是询价 → 不产"一刀切

**询价动词清单**：能走吗、能接吗、还有吗、还能做吗、有位置吗、好放不、放舱吗、quote、PLZ、报一下、多少

**操作通知动词清单**：开舱、截关、截单、催单、放舱、@所有人、@xxx、通知、提醒

### 34. 柜型配价按证据推（不硬套三档）

**柜型配价证据优先级**（从高到低）：
1. **图片表头**：明确写了 "20'/40'/40NOR" 或类似 → 按表头列对应
2. **文字明确**："20GP 2800 / 40HQ 3600 / 40NOR 3800" → 按文字对应
3. **群/发布人知识**：该群/该发布人通常只报两档（如韩琦价卡 A/B/B）→ 按两档配
4. **三段数字 + 上下文支持三档** → 逐档配价
5. **无法确定** → 保留原文，不猜、不造，标"柜型未确定"

**关键修正**：
- ❌ 不再"三段数字 → 自动对应 20GP/40HQ/40NOR"
- ✅ 先看表头、看文字、看群惯例，没有证据不硬套第三档
- ✅ 数字重复（如 2800/3600/3600）不自动认为第三档是 NOR，要标"疑似 NOR 但无证据"

### 35. via 处理修正（不并入目的港字符串）

**目的港只放港口；走法放现有"航线服务"字段或备注**：
- ❌ 不再 `基本港 via CARIOCA` 并入目的港字符串
- ✅ via 走法 → 目的港只放港口名，走法放"航线服务"字段或备注
- 示例：`Santos via Panamax` → 目的港=`Santos`，航线服务/备注=`via Panamax`

### 36. 证据冲突处理（不统一"表头优先"）

**判断消息时间和适用范围**：

| 情况 | 处理 |
|---|---|
| 正文写"本周降 200" + 旧图片表头是原价 | 按正文（新消息的调价） |
| 正文写"参考价" + 图片表头是报价 | 按图片表头（正式报价） |
| 无法判断哪边是最新/正式 | 标"证据冲突"，保留两处原文，不自动选 |

**关键修正**：
- ❌ 不再统一"表头优先"
- ✅ 判断消息时间（哪个是新的）和适用范围（哪个是正式报价）
- ✅ 不能确定才保留冲突，让人工判断

### 37. 解析前必查本群历史纠正（记忆层）

**每条新消息解析前，先调一次记忆接口拉本群历史人工修正**，再开始提取：

```
GET http://127.0.0.1:8795/api/memory-lookup?group=<来源群名>
Header: x-push-token: <推送 token>
```

返回两类参考：
- `field_defaults`：本群该字段人工最常填的值（≥2 次），如 `柜型=40HQ/HC`、`目的港=Istanbul`、`目免=14`
- `corrections`：高频纠正对（≥2 次），如 `"华南基本港"→"Ningbo"`、`空→40HQ/HC`

**用法**：
1. **字段原文没写/拿不准时**：先看 `field_defaults` 有没有本群惯例值。有唯一高频值就按它填，备注标 `AI判断=是` 并注明参照本群历史。
2. **原文写法跟 corrections 的 old 匹配时**：按 new 填（如原文写"华南基本港"，本群历史被改成 Ningbo）。
