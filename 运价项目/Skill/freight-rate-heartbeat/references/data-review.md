# 台账数据审查 agent（随拉取一起、经许可创建的第二个定时任务）

**用途**：只读地体检运价台账 `freight_manual.db` 的入库数据质量，发现脏值 / 缺主数据 / 判定异常，出一份给人看的报告 + 修复建议。
**红线**：它**绝不写业务表**——审查 = 读接口 + 汇报，任何"改"都交人工在台账「待审核」页或「主数据库」做。

## 何时建、和拉取任务的关系
建"拉群运价" cron 时，**先征询用户许可**，再一并建这个审查 cron（两者相互独立，可分开停/启）。
频率建议低峰每天一次（如 `0 21 * * *` 收盘后，Asia/Shanghai），不必和拉取同频。

## 数据来源（全部只读、免写令牌；令牌也只用于读）
- **先摸清结构**：`GET /api/bootstrap`、`GET /api/options` 拿字段清单与筛选枚举；结合台账建表口径（`manualdb` DDL：表/列、价格列 INTEGER+非负 CHECK、`valid_from/valid_to` ISO CHECK、`origin` 默认、`content_key`/`supersedes` 语义）和 `Database/docs/agent-input-contract.md`，先建立"每列该长什么样"的判断基线，再谈审查。
- `GET /api/audit` —— 台账**全库机械校验体检**，返回每条不达标行的 `{kind, pol, pod, carrier, errors:[{field,input,msg}]}`。主力信号。
- `GET /api/pending?status=failed&kind=` —— 被机械校验打回、卡在待审核的条目及其 `errors`（agent/人工录入传坏的）。
- `GET /api/master?full=1` —— 合法值全集（ports/port_groups/carriers/routes），用来区分"数据本身脏" vs "主数据缺登记"。
- `GET /api/rates`、`GET /api/space`（扁平，limit 拉一批）—— 做重复、当前价、时间戳等交叉核对。

## 审查清单（= 本项目测试踩过的坑 + 台账值规范，逐类扫，命中即记 例证+建议）

1. **核心字段没命中主数据**（起运港/目的港/船司/航线）。要分两类报，别混：
   - *主数据缺登记*：如语义起运港群 `华南基本港` 未进 `port_groups` → 建议去「主数据库→港群」补，而不是驳回数据。
   - *数据脏*：编出来的港口/船司。⚠️ 特别盯**伞形区域词**当航线的坑：`拉美/地东` 这类是台账里的 **region**（被多条航线共用），不能当 `航线` 值，填了必被判歧义打回——遇到就提示"改留空或选具体航线"。
2. **必填为空**：运价缺 `柜型/海运费USD/有效期`；舱位缺 `起运港/船司/舱位类型/有效期`（`船名航次` 选填——现舱消息常只报港口+舱位类型不给船名，别为它打回，也别编一个）。
3. **价格/天数非整数或负**：`freight_usd / price_usd / free_days / dead_freight / transit_days / box_qty`（台账列是 INTEGER+非负 CHECK，人工/旁路可能塞进脏值）。
4. **有效期不规范**：`valid_from/valid_to` 非 ISO `YYYY-MM-DD`、只填一端、或 `起 > 止`。
5. **枚举越界**（台账服务端**不兜底**，历史/人工数据最易脏）：柜型 ∉ `{20GP, 40HQ/HC, 40NOR}`；舱位类型 ∉ 8 档（尤其旧值"报备"、以及 `40GP/40HC` 未并成 `40HQ/HC`）。
6. **重复 / 当前价异常**：同一 `起运港+目的港+船司+消息原文` 有多行都是"当前生效/当前有效"（应只一条、其余"已被覆盖"）；或"更新"没留痕、`supersedes` 断链。
7. **消息时间可疑**：大量 `message_time` 相同且≈某入库时刻 → 说明 agent 没带真实群消息时间、被盖了 now，会让折叠视图"当前价"判错、历史排序乱。（agent 口径服务端保留传入值，正常应各不相同。）
8. **溯源断链**：`message_text`（消息原文）空或过短；本心跳产的记录里若是引用回复，`消息原文` 应自带 `——引用 <时间> <发送人> mID=<…>——` 引用块，缺了说明走了旧装配路径。
9. **图片缺口**：记录有 `图片名` 或原文里含 `mediaId=@…`，但 `Database/images/` 下无同名/同前缀文件 → 看板渲染"图片未同步"。
10. **来源值异常**：`origin` 出现非 `manual/agent`（如旧遗留 `heartbeat`）→ 有旁路写入混进来，需查来源。
11. **别把"船司 ≠ 船名里的公司"当错误**：共船 / 舱位互换（VSA）是常态，船东 ≠ 报价承运（见 `extraction-rules.md#18`）。要盯的是**反过来的坑**——`船司` 被从船名（如 `MSC OSCAR`）硬凑出来：这种建议留空或改回报价来源的承运，**不要**把 `船司` "纠正"成船名里的公司。
12. **带价现舱是否双入**：同一 `消息ID` 下应同时存在一条运价和一条舱位。运价应有 `海运费USD`，不应带 `价格USD/舱位类型/箱量/箱型箱量`；舱位应有箱量、舱位类型或截关等舱位事实，不应重复 `价格USD`。缺任一表时提示回查抽取并重跑，不手工补价格或箱量。

## 出建议的原则（先懂结构 → 归因 → 给可执行改法）

每条命中都要走完三步，给的是**用户能直接照做的改法**，不是空泛"数据有问题"：

1. **归因**：判定属于——① 数据本身脏（值不合规）；② 主数据缺登记（合法值不在库里，如新港/新航线/语义群）；③ 传入口径错（如把 region 当航线、日期发区间串、价格带小数）。不同因，改法不同。
2. **给具体改法**：点名到"哪个字段、改成什么、走哪个端点/人工步骤、影响是什么"。示例：
   - 把 `航线` 由 `拉美` 改成具体航线（如 `南美西`）或留空；
   - 「主数据库 → 港群」补一条 `华南基本港`（成员：…）后再放行相关 failed；
   - 「待审核」页把该条 payload 的 `海运费USD` 改成整数 `2850` 再放行；
   - `柜型` 里的 `40GP/40HC` 归并成 `40HQ/HC` 重传；
   - 缺图：把对应 `mediaId` 的原图下载进 `Database/images/`（文件名以 mediaId 开头）。
3. **只建议、不自动改库**：审查 agent 全程只读。落库/补主数据/删重复一律人工在台账做。**若某个错其实源于本 skill 的抽取逻辑**（同一类反复出现），在建议里点出来：改 `scripts/record_builder.py` 模板或 `references/extraction-rules.md` 口径，而不是让用户一条条手改。

## 输出（给人看）
按 kind 汇总每类**命中数 + 3~5 条例证**（港/司/价/字段/具体错误）+ **可执行建议**（哪些补主数据、哪些在待审核页修 payload 或驳回、哪些删重复）。
默认只在汇报消息里说清楚；**不静默写文件**。要落盘报告须用户明说（存 `heartbeat-data/audit_report_<日期>.md`）。
